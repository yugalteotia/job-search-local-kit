# Local job-search workflow

## Current controls — 13 October 2026

`mode: read_only`, `submissions.enabled: false`, or `apply-now --dry-run` (alias `--read-only`) blocks every application upload, answer and submission claim. Only Naukri native Apply and LinkedIn Easy Apply are in scope; other sources and employer boards are reversibly disabled and their records preserved. Each provider has independent `apply_enabled`, `scheduled_apply_enabled` and `max_new_attempts_per_run: 10` controls. The two caps are independent: 10 Naukri plus 10 LinkedIn new attempts, for scheduled runs and Run Now. The legacy `max_submissions_per_run` is an equal-valued alias for the new-attempt cap. Fresh blocked preflights and locked uncertain outcomes consume a slot; resume-only preflight repairs without a new claim consume zero slots; continuing a recorded attempt retains its claim and consumes no new slot. A saved unclaimed draft consumes a new slot only if its first durable submission claim is created. Jobs are handled sequentially with existing waits and additional pacing; CAPTCHA, restrictions and site limits stop only the affected provider. Generic-resume restoration failures stop Naukri. General live runs require a real job-bound provider proof. An explicitly scoped manual `--job-id` can establish a provider's first proof; the timer cannot bootstrap an unproven provider.

Run `python3 workflow config check` and `python3 workflow portals` for configured flags and proven capabilities. `config naukri-live --scheduled` and `config linkedin-live --scheduled` independently enable proven providers. `config read-only` disables all live lanes. Timer (`daily --scheduled`), CLI (`apply-now`) and dashboard Run Now call the same `pipeline_v2.run`, sharing pause, run lock, dedupe, fit, resume, questionnaire and proof gates. Manual runs work with the timer disabled. The four existing slots are 08:30, 12:30, 16:30 and 20:30 IST.

Current suitability policy: substantial Java with Spring/Spring Boot backend development, a compatible confirmed-experience range (including approved reasonable 3-year near-misses), eligible India/India-remote location, live listing and exact-job dedupe. Clearly incompatible seniority or a different primary stack is excluded. Kafka, Kubernetes, cloud, Redis, frontend framework and other secondary gaps are recorded in `fit_json.result.interview_preparation_gaps`; they do not automatically reject a matching role. Resumes remain verbatim confirmed evidence; mandatory screening answers stay truthful, and unknown facts become NeedsAnswer. Spelled-out and numeric experience ranges retain their hard minimums.

Native Naukri discovery uses the isolated direct Chrome profile, verifies the experience/freshness/newest controls, records actual cards, and reviews only this sweep's candidates. It preserves unknown posting times and skips unchanged reviewed cards and locked uncertain jobs. Earlier sections below describe historical migration stages.

Naukri uses its isolated direct Chrome session, restores the generic resume in every live outcome, and keeps a crash-recovery marker until restoration verifies. Applied requires a complete Applied Jobs history with exact job identity, including the native history API when its UI row has no link. Listing-only outcomes remain reconciliation pending and locked. LinkedIn uses its own automation profile, native Easy Apply controls and job-specific PDFs; unknown required facts become job-scoped NeedsAnswer drafts, and potential submissions without exact positive confirmation remain locked Uncertain. Dedicated profiles and credentials stay outside this repository. Inspectors block application mutations.

Playwright runs through the guarded `tools/private_playwright.py` launcher. Each worker can own one tab, and no more than three worker connections may hold tabs at once. The proxy records the numeric tab ID returned by the connector, reuses that tab for later `browser_tabs new` navigation, and blocks selection or closure of IDs it did not create. The connector startup opens a `connect.html` Welcome page; the proxy matches its relay port to the listener owned by that exact MCP process, records the returned tab ID, and closes it only after the connection is established and worker cleanup runs. It never closes a Welcome page based on title/URL alone. Missing IDs, ambiguous ownership, or failed closes remain open and are reported as uncertain. The connector exposes session-scoped indexes rather than stable Chrome target IDs, so cleanup is limited to the same MCP connection that received the ID. Per-run job and Welcome tab events and counts are written to `.workflow/runs/<run-id>-tabs.jsonl` and included in the run JSON when emitted.

## Historical migration notes — superseded by current controls above

The four Asia/Kolkata slots are 08:30, 12:30, 16:30 and 20:30. Submissions remain blocked by configuration and the application state machine.

A bounded read-only source sweep writes its machine-readable result under `.workflow/runs/<run-id>.json`. It reports actual pages checked, leads, original JDs verified, fit decisions, queue state, blockers, errors, and artifacts. A capped or failed sweep is Partial or Blocked, not Success. Portal leads alone are never treated as verified applications. The Optum 2388999 history key remains terminal and cannot be retried.

Portal leads enter a separate persistent queue awaiting original-JD verification. India-based engineering ATS postings enter the JD review queue; deterministic experience and essential-skill checks produce Medium, Low, or Unresolved with excerpts. A complete evidence packet can be evaluated with `python3 workflow fit JOB_ID packet.json`; only a passing High-fit packet enters the resume queue. Resume and application queue consumption remains disabled.

Review selection is capped in `config/job_search.yaml`: at most 20 original-page checks, 30 detailed JD reviews overall, and five per employer per run. A live ATS page is not automatically a substantive JD: detailed review requires duties or qualification text, not only a title/location shell or company boilerplate. Review ranking favors relevant titles, Java/Spring/backend evidence, required experience, and recent checks. `python3 workflow leads resolve --limit N` checks the best recent Java/backend portal leads first and interleaves sources; it records an explicit terminal state for unmatched, unavailable, or blocked pages so they do not inflate the pending queue. The bounded audit is in `.workflow/reviews/20260928T121404-fair.json`; portal resolution is in `.workflow/reviews/20260928T121144-leads.json`. Portal navigation/category links are `NotAJob`; a portal posting without a matching enabled original employer page cannot become High.
