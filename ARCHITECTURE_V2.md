# Code-driven workflow migration (28 Sep 2026)

Current execution controls (14 Oct 2026): `job_config.live_provider_enabled` gates Naukri native Apply and LinkedIn Easy Apply independently. Both share `pipeline_v2.run` across timer, CLI and UI, a run lock, pause, exact-job dedupe, current fit evidence, bound PDFs and durable claims before submission. Each provider is independently capped at 10 new attempts per run. Only new claims consume slots, including claimed blocked/uncertain outcomes. Unclaimed preflight skips and existing claimed continuations consume no new slot. Confirmations are counted separately. Suitability uses Java/Spring backend work, compatible confirmed experience including approved 3-year near-misses, eligible location, live state and dedupe; secondary technology gaps are recorded for interview preparation. Read-only/dry-run cannot upload, answer, recover a profile upload or claim. Timers additionally require each provider's scheduled flag and a real provider proof; exact-job manual proof runs cannot be initiated by a timer. Other sources and boards are reversibly disabled. Naukri confirmation requires complete exact-ID Applied Jobs history, with structured native history API identity when DOM links are missing; listing-only outcomes stay locked and pending. LinkedIn requires positive application-sent confirmation tied to the exact job, and preserves unsubmitted drafts for missing facts. Naukri generic restoration is verified inside its live session and recovered from a durable marker after crashes. Both use distinct private automation profiles. See [WORKFLOW_README.md](WORKFLOW_README.md) for current commands and proof; the dated text below records prior migration stages.

Automatic pending-outcome reconciliation (`tools/outcome_reconcile.py`, 14 Oct): before discovery/application work and after worker cleanup, the shared `pipeline_v2.run` lock also owns read-only history reconciliation. Normal exceptions trigger a read-only after-crash check; a forcibly terminated process is reconciled before the next run. The reconciler never clicks Apply, opens screening forms, uploads resumes, or sends answers. Complete history, the correct isolated account/session, and exact job IDs with positive Application Sent evidence are mandatory. Naukri server timestamps must not predate a still-pending claim. Missing/partial history preserves locks; a resolved job remains blocked by Applied/history dedupe and existing permanent exclusions. An incomplete attempt can become confirmed without a new claim or invented answer delivery. Original progress/outcomes and inspector/generic-resume facts are preserved. Tracker dates use server submission dates. Confirmations enter a durable notification outbox; successful desktop alerts are deduplicated, and failed deliveries are retried without reopening applications. Dry-run and session-only diagnostics perform no reconciliation browser/state actions. LinkedIn reconciliation requires a verified Applied filter and complete explicit count; the current redirected job tracker does not expose these, so uncertain LinkedIn outcomes remain locked rather than using listing text as history proof.

`config/job_search.yaml` is the only human-editable global setting. `tools/job_config.py` validates the portal host allowlist, public ATS board tokens, limits, strict High-fit gates, four IST slots, concurrency, retention, and the read-only submission lock at startup. If the latest exact page is title-only, it cannot be fit reviewed from an older saved JD until a substantive JD is visible again.

# Code / config / agent boundary and the Naukri hand-off (30 Sep 2026)

**Code (fast, deterministic):** discovery, deduplication, freshness, exact-excerpt fit validation, resume assembly, browser driving, network phase guard, proof gates, views. **Config (person-specific):** `config/job_search.yaml` (sources, limits, lane switches) and `config/candidate.yaml` (identity, skill evidence catalogue work/project/gap with verbatim excerpts, reusable questionnaire answers, resume assembly rules). `tools/candidate.py` fails loudly (`workflow master-check`) if an excerpt no longer exists in `master-resume/*.tex`, `SEARCH_PROFILE.md` or `APPLICATION_PROFILE.md`. **Agent (judgement):** not part of the scheduled run. Borderline JDs are left as near-misses (quick view) and may be reviewed on demand by writing a fit packet for `workflow fit`, which code still validates.

Scheduled Naukri lane, in order (all in `pipeline_v2`): portal-native verification → `auto_fit` (JD lines → essential/optional/duty context → catalogue basis; `fit_engine.evaluate` is the only gate; uncertain duplicate, seniority words, 4+ years, essential Kafka/cloud/Kubernetes/other unsupported stack all stop it; unverified generic fundamentals such as OOP/multithreading are recorded, never claimed) → `bind_verified_portal_id` + `apply_fit_decision` (Shortlisted, QueuedResume) → `auto_resume` (bullets verbatim from the master `.tex`, priority-ordered, low-priority bullets dropped instead of shrinking type; automated one-page/font/link/ink-margin/text checks; `visually_clean` only while `render_resume.py` matches the hash in `.workflow/resume-template-approval.json`) → `naukri_native_worker` (High before strong-Medium, max 2 jobs tried and 1 claim per run, 6 h back-off then user hand-off after 3 pre-claim stops).

Worker facts learned from real runs: the Applied Jobs list scrolls inside its own container (scroll it, then click the 1 px sentinel); the generic-resume restore must run inside the live browser session after the network guard is removed (`_browser_session`); a questionnaire can continue with Yes/No radio choices after a text question. Radio answers are chosen only from `answers.rules` and must equal the clicked option and the request payload. After any Save, an unanswerable next question leaves the attempt Uncertain and locked (never retried); the pending question is stored as `pending_question` and shown in the quick view.

Read-only mailbox reconciliation: `python3 workflow reconcile <capture.json>` labels messages exact / probable / ambiguous / company_only / unmatched, flags history gaps (applied elsewhere, not in tracker) and conflicts, and never changes the database. History gaps also block matching employer/role candidates in the Naukri worker. Gmail is not read automatically: capture message metadata from the signed-in mailbox first.

`python3 workflow apply-now [--dry-run]` (`tools/apply_now.py`) starts the scheduled pipeline immediately by calling `pipeline_v2.run(scheduled=True)`, the same function as the systemd `workflow daily --scheduled`; it adds only progress lines, the service PATH when `npx` is missing, and a final summary. It exits 2 without starting if another run holds the lock, the workflow is paused or the schedule is disabled. `--dry-run` is the pipeline's test mode: discovery, fit review and resume preparation run as usual, but the Naukri worker only reports `WouldSubmit` and opens no form.

# Multi-portal workers, shared core and dashboard (30 Sep 2026)

**Entry points → one pipeline.** systemd (`workflow daily --scheduled`), `workflow apply-now [--dry-run]` and UI Run Now all reach `pipeline_v2.run(scheduled=True)`; `tools/core_run.py` is the CLI/UI front (`execute`, `start_detached` via a transient `systemd-run --user` unit with the service PATH and `JOB_SEARCH_TRIGGER`). Manual runs pass `manual=True`, so they work while the timer/schedule is disabled, but they never start while `control.json` is paused or another run holds `.workflow/daily-run.lock`. `runs.trigger` records timer/cli/ui.

**Portal registry (`tools/portals/`).** `Capability` = DiscoveryOnly | ApplyReady | Blocked, recomputed each run and stored in `portal_capability`. ApplyReady (Naukri only today) requires: worker implements apply, `naukri_worker.enabled`, `portal_workers.naukri.apply_enabled`, a valid job-bound proof marker (`job_db.portal_path_verified`), no pending resume restore, healthy last discovery. `job_config` refuses `portal_workers.<other>.apply_enabled: true` unless `.workflow/portal-proof/<portal>.json` exists. LinkedIn, Indeed, Cutshort and ATS stay DiscoveryOnly; Foundit is Blocked while its discovery returns no cards. `workflow portals` prints capabilities.

**Crash recovery.** `tools/recovery.py` (start of every run): stale `Resuming` queue rows return to `QueuedResume`; unclaimed `InProgress/Preparing` Naukri jobs return to `Prepared`; claimed attempts stay locked. The generic-resume marker `.workflow/profile-restore-pending.json` is written before any role-resume upload and removed only after a verified restore; the worker recovers it (or alerts and blocks the lane) before doing anything else. Pause is honoured before each stage, each candidate and the claim; a claimed attempt still finishes its own defined stop.

**Naukri multi-question fix.** Phase guard `reopen` phase: after a Save, if the chat stops without a new question or commit, the same claimed attempt reopens the same live listing (one guarded `show`, max 2, never a new claim, no answer replay; a repeated question ends as Uncertain). Yes/No radio answers come only from `config/candidate.yaml` rules and must match the clicked option and request payload.

**Dashboard.** `python3 workflow ui [--port 8765]` prints `http://127.0.0.1:8765/#token=...`. stdlib server bound to 127.0.0.1; token in `~/.local/share/job-search-private/ui-token` (0600) required on every `/api/*` call; Host/Origin checked; CSP without inline code. Pages: Run (Run now, Dry run, Pause/Resume, live progress from `.workflow/progress/<run>.jsonl`), Handoffs (needs answer, Uncertain with the pending question, urgent, applied, evidence links), Tracker (quick/detailed, allowlisted columns), Portals (capabilities, discovery toggles, Naukri lane switch; other portals show "Needs proof"). Responses are scrubbed of contact details; profile, answers, cookies and pre-submit packets are never served.

# Questionnaire loop, dedupe and master build (30 Sep 2026)

**Questionnaire states.** A claim (`begin_attempt`) makes the job `SubmissionUnconfirmed` and the attempt `uncertain` (in flight, locked). If the loop stops *before any Save is in flight* (unknown answer, answer not among the radio options, unsupported format), the worker runs a read-only check (`_verify_incomplete`): guard shows no completion/commit and no denied request, listing not Applied, full Applied Jobs history has no exact match. Only then `job_db.mark_attempt_incomplete` (evidence re-validated inside the DB layer) sets the attempt `incomplete` and the job `NeedsAnswer` (alerted as a handoff). Any doubt, any ambiguous Save, a repeated question, or a failed check stays `uncertain`/`SubmissionUnconfirmed`. Progress is persisted per Save in `jobs/<slug>/naukri-native-progress.json` (question text and fact refs only). When the pending question becomes answerable from confirmed facts, `resumable()` picks it first; `resume_incomplete_attempt` reuses the same attempt (job `InProgress`, no new claim, no answer replay, max 2 resumes, one claimed attempt per run); the job returns to `SubmissionUnconfirmed` before the first continuation Save, and `Applied` still needs positive job-bound proof. A continuation that dies mid-flight is locked as unconfirmed by `recovery.py`.

**Dedupe.** Exact IDs decide. `_portal_duplicate_check`: exact portal / employer requisition match blocks; unapplied leads and Closed/Excluded history never count; different exact IDs in the same namespace are different postings unless an earlier attempt is unresolved and the title is near-identical; title similarity only covers records that cannot be compared by ID. Mailbox history gaps (`response_reconcile`, schema 2) keep the role and requisition: an equal requisition ID blocks, different IDs do not, a role-only gap blocks only the same role, an employer-only gap never blocks.

**Master resume.** `python3 workflow master-build [--install --visually-reviewed]` (`tools/master_build.py`) builds `master-resume/Yugal_Teotia_CV.pdf` with pdflatex if present, else tectonic (`~/.local/bin/tectonic` 0.17.0, sha256-verified). The XeTeX build copy loads Latin Modern OpenType with common ligatures disabled so text extraction is `workflows`, never `workﬂows`; the source `.tex` stays pdfTeX-native. Install needs all automated checks (one page, all master text extracted, contact links, embedded fonts, ink margins, no ligature codepoints, no stale "Present" after 30 Sep) plus a recorded visual review of the exact PDF hash; the previous PDF is backed up in `.workflow/backups/`. The `.tex` had a layout-only edit (top/bottom 0.30 in, list and section spacing) so the added AWS lines fit one page.
